# Role `nas_proxy`

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

Part of `nas.yml` (row in `docs/conventions/ansible.md`).

Then `nas_proxy` (`dc@nas_proxy`, container `nas-proxy`: Traefik, file provider only, no Docker socket, Let's Encrypt by DNS-01 with the OVH key `nas_ovh_application_key`/`_secret`/`nas_ovh_consumer_key`, `acme.json` `0600` root under `docker_base_path`; every router asks for the one wildcard `nas_proxy_wildcard_domain`, `*.sylvain.cloud`, ADR 0031, empty for one certificate per name; the former per-name certificates, still in `acme.json`, win over it until removed) fronts five names; out of reach of the PikaPods Uptime Kuma, their certificates are checked on the NAS itself by the daily `nas-proxy-cert-check.timer` (`files/cert_check.py`, Python stdlib against `127.0.0.1:8443` with each name as SNI, system CA store), which pushes up, or down under `nas_proxy_cert_check_min_days`, to the `Certificats NAS` monitor (`uptime_cron_nas_cert_url`). The apps behind it are out of that Uptime Kuma's reach too: every 5 minutes `nas-health-check.timer` (`files/health_check.sh`, curl through `127.0.0.1:8443` with each name as SNI and Host, system CA store: the path of a browser at home, TLS included) asks Jellyfin's `/health` and MediaManager's `/api/v1/health` (`nas_proxy_health_checks`) and pushes ONE result (up when every app answers, else down with curl's error of each failing app) through `uptime-push` (role `uptime_push`, a `meta` dependency) to the single `Healthcheck NAS` monitor (`uptimekuma_monitor_push.health_nas`, `tofu/pangolin_config/health_nas.tf`: a 10 min window and one 5 min retry, so two failed checks in a row page, a silent NAS pages after 15 min). The push URL (`uptime_health_nas_url`, read by `nas.yml` into `nas_proxy_healthcheck_url`) lives in `health/nas.curl`, `0600` root, `no_log`; an empty one removes that file and the apps are checked without pushing (the former `health/jellyfin.curl` and `health/mediamanager.curl` are removed). `https://media.sylvain.cloud` (Jellyfin), `https://nas.sylvain.cloud` (UGOS's UI, `http://<NAS LAN IP>:9999` behind it) and `https://mediamanager.sylvain.cloud` (MediaManager trial, `http://mediamanager:8000` on the internal `mediamanager_proxy` network that `dc@nas_proxy` creates and `dc@mediamanager` joins as external, hence `mediamanager` after `nas_proxy` in `nas.yml`: the trial depends on the proxy, never the other way round, so removing it or a failed `dc@mediamanager` never takes `media`/`nas.sylvain.cloud` down), with or without `:8443`, at home and through the Pangolin client (public A records `tofu/dns/media.tf`/`nas.tf`/`mediamanager.tf` to the NAS's LAN IP, beating the `*.sylvain.cloud` wildcard, each in Blocky's `blocky_rebinding_allowed_domains`; private resources `media.sylvain.cloud` and `mediamanager.sylvain.cloud`, site `nas`, `nas-proxy` on the `newt` network, TCP 443 and 8443, and `nas`, site `proxmox-lxc`, LAN IP, TCP 22, 443, 445, 8443, 9999). Jellyfin's and MediaManager's routers have no source filter: both Pangolin resources reach the same `nas-proxy` ports, so a `jellyfin` role member can reach MediaManager's login page by asking for its name (and the other way round), like any LAN device; each app's own account is the gate. `https://prowlarr.sylvain.cloud` and `https://qbittorrent.sylvain.cloud` (MediaManager's tools, `http://mediamanager-gluetun:9696` and `:8080`: gluetun joins `mediamanager_proxy` too, its firewall lets the network's subnet in and nothing else out) work the same way, with their own routers, A records (`tofu/dns/prowlarr.tf`, `qbittorrent.tf`), Blocky entries, certificate-check names and private Pangolin resources, bound to the role `mediamanager-admin` only; not in `nas_proxy_health_checks` (their containers exist only once the VPN key is set). **Pocket ID in front of Prowlarr and qBittorrent**: when the Tofu outputs `pocket_id_mediamanager_tools_client_id`/`_client_secret` and `pocket_id_issuer` exist (client `mediamanager-tools`, `tofu/pangolin_config/pocket_id.tf`; read in `defaults/main.yml`, nothing rendered otherwise), the compose gets a third service `oauth2-proxy` (container `nas-proxy-oauth2`, `quay.io/oauth2-proxy/oauth2-proxy` pinned by tag and digest, distroless, non-root, `cap_drop: ALL`, read-only, `newt` network only so it reaches `id.sylvain.cloud` by the NAS's normal egress and never through gluetun, no published port, no healthcheck: no shell in the image; `mem_limit` 64m is an estimate, ~2x a Go proxy's 15 to 30 MB RSS, to be re-set on `memory.peak`). The `prowlarr` and `qbittorrent` routers get `[oauth2-auth, mediamanager-headers]`: `oauth2-auth` is a forwardAuth to oauth2-proxy's root (« static upstream » setup of its docs: `--upstream=static://202`), which answers 202 with a valid session of group `mediamanager-admin`, else a 302 straight to Pocket ID (`--skip-provider-button`); the return URL is built from Traefik's `X-Forwarded-Host`/`-Uri` (`--reverse-proxy`), and `--whitelist-domain` admits only both names, any port. A router per name, `<name>-oauth2` (`Host && PathPrefix(/oauth2/)`, priority 1000), sends `/oauth2/` (start, callback) to oauth2-proxy; the callback comes from `X-Forwarded-Host/-Proto` (`--reverse-proxy`), so 443 and 8443 are both registered in the Pocket ID client. One session cookie per name (`__Host-oauth2`: Secure, Path=/, no Domain, never `.sylvain.cloud`); cookie secret = 32 hex characters derived from `backup_passphrase` (no SOPS key). PKCE S256, `--allowed-group=mediamanager-admin` on the `groups` claim, plus the client's own `allowed_user_groups` (double gate). The `mediamanager`, `media` and `nas` routers are untouched. Behind it the apps ask for no login of their own (role `mediamanager`, `mediamanager_ui_sso_only`); `mediamanager_local_login: true` brings them back (its README). Break glass if Pocket ID or the proxy is down (Traefik then fails closed: 5xx, or a sign-in page that cannot finish): SSH tunnel to the NAS's `127.0.0.1:8080` (qBittorrent; Prowlarr's `9696` only with `mediamanager_local_login: true`), published by gluetun, bypasses Traefik; `ansible/roles/mediamanager/README.md`). No errors middleware: a backend's own 401 (Prowlarr API, expired app session) reaches the client unchanged; MediaManager reaches both apps on the internal network, not through Traefik. Only `ugos` is LAN-only (`ugos-lan`). `8443` is published by Docker on `nas-proxy`. The host's `443` is **not** published: it is held by a second service of the same compose, `forward` (container `nas-proxy-443`, same Traefik image, `network_mode: host`, TCP passthrough to `nas-proxy`'s unpublished `websecure-forwarded` entrypoint `172.30.96.10:8444` with PROXY protocol v2, trusted from the host's `jellyfin_media` gateway `172.30.96.1` only, so `ugos-lan` and Jellyfin still see the client IP). Port 443 is free only while UGOS's "redirect HTTP/HTTPS to the UI's HTTPS port" setting is unticked (`defaultHttpsRedirectEnable` in `/etc/nginx/config.json`, a 307 to `:9443` in `ugreen_ssl_redirect.conf`); if a UGOS update ticks it again and nginx starts first, the relay's Traefik exits on bind and Docker retries it (back-off up to 1 min) while `nas-proxy` and `:8443` keep running (nothing orders nginx before Docker: if the relay holds 443 first, nginx fails and the whole UGOS UI with it; `docker stop nas-proxy-443`, restart nginx, untick, `docker start nas-proxy-443`) — a published 443 would instead fail the container create, hence `up`, and `dc@`'s `ExecStop` would stop `nas-proxy` on every retry. The role flushes its handlers then fails (`tasks/host_https_port.yml`, `ss -p`) when anything but the relay listens on the host's 443. Port 80 stays with UGOS's nginx (DNS-01 needs none).

Exposure (checked 2026-11-11 with `ss -ltn`: 8443 and 8096 listened on `0.0.0.0` and `[::]`, and eth0 holds a global IPv6): the published 8443 and Jellyfin's 8096 are bound to the NAS's LAN IP (`nas_proxy_bind_address`, `jellyfin_bind_address`, `ansible_host`), plus `127.0.0.1:8443` for the health probe and the certificate check. Pangolin's paths do not use them (the LXC Newt reaches the LAN IP, the NAS Newt the container's 443 on the `newt` network). The TLS option `default` has no CBC suite (same list as Pangolin) and `forwardAuth` no longer trusts incoming `X-Forwarded-*` (nothing upstream sets them: Pangolin only tunnels the TCP). Left undone: the host's 443 (`forward`, `*:443`; only the `ugos` router answers there, 403 outside the LAN), and an `ipAllowList` on the `media`, `mediamanager`, `prowlarr` and `qbittorrent` routers, **delivered off** (audit ex9, 2026-11-11). The Newt of the NAS arrives from the `newt` Docker network, whose subnet Docker chooses (172.18.0.0/16 on 2026-11-11), so a range cannot name it until it is pinned: `newt_subnet` (role `newt`, empty by default, `host_vars/nas`) pins it, and when it is set the middleware `nas-apps-lan` (`ipAllowList`: the LAN `nas_proxy_ugos_source_ranges`, `nas_proxy_newt_subnet`, and `nas_proxy_forward_trusted_ip/32`) goes on those four routers, ahead of `oauth2-auth`. The last range is the host's gateway on `jellyfin_media`: the health probe and the certificate check reach `127.0.0.1:8443` through docker-proxy, which Traefik sees as `172.30.96.1` (read with `ss -tn` on 2026-11-11); without it the `Healthcheck NAS` monitor would go down on a 403. The LAN keeps its address through Docker's DNAT on 8443 and through the PROXY protocol of the relay on 443; Pangolin clients arrive from the Newt container; anything else (a global IPv6 address, a Docker network that is not `newt`) gets a 403. **Turning it on** changes the subnet of an existing network, which Compose does by recreating it, and refuses while `nas-proxy` and `nas-proxy-oauth2` (project `nas_proxy`) are still attached: in order, `systemctl stop dc@nas_proxy` on the NAS (media, MediaManager, Prowlarr, qBittorrent and the 443/8443 UI are down from here: Pangolin clients and the LAN lose them), set `newt_subnet: 172.30.98.0/24` in `host_vars/nas`, `ansible-playbook nas.yml --tags newt` (`dc@newt` restarts: `newt` and its socket proxy restart, the `nas` site is offline for a few seconds, the `newt` network is recreated on the new subnet, no other container is attached to it), then `ansible-playbook nas.yml --tags nas_proxy` (renders `nas-apps-lan`, restarts `dc@nas_proxy`: `nas-proxy`, `nas-proxy-443` and `nas-proxy-oauth2` rejoin `newt`). Check: `docker network inspect newt` (subnet and the three members: `newt`, `nas-proxy`, `nas-proxy-oauth2`), a Pangolin client opens `https://media.sylvain.cloud`, the LAN opens it with and without `:8443`, `systemctl start nas-health-check.service` ends 0 and `Healthcheck NAS` stays up. Back: set `newt_subnet: ""`, stop `dc@nas_proxy` first again and run the same two commands (the `newt` network is recreated with a subnet chosen by Docker, the filter disappears). Never run a bare `nas.yml` with `newt_subnet` changed and `dc@nas_proxy` up: `dc@newt` would fail to recreate the network. The oauth2-proxy gate stands in front of Prowlarr and qBittorrent on every path.
