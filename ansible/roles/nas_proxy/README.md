# Role `nas_proxy`

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

Part of `nas.yml` (row in `docs/conventions/ansible.md`).

Then `nas_proxy` (`dc@nas_proxy`, container `nas-proxy`: Traefik, file provider only, no Docker socket, Let's Encrypt by DNS-01 with the OVH key `nas_ovh_application_key`/`_secret`/`nas_ovh_consumer_key`, `acme.json` `0600` root under `docker_base_path`) fronts five names; out of reach of the PikaPods Uptime Kuma, their certificates are checked on the NAS itself by the daily `nas-proxy-cert-check.timer` (`files/cert_check.py`, Python stdlib against `127.0.0.1:8443` with each name as SNI, system CA store), which pushes up, or down under `nas_proxy_cert_check_min_days`, to the `Certificats NAS` monitor (`uptime_cron_nas_cert_url`). The apps behind it are out of that Uptime Kuma's reach too: every 5 minutes `nas-health-check.timer` (`files/health_check.sh`, curl through `127.0.0.1:8443` with each name as SNI and Host, system CA store: the path of a browser at home, TLS included) asks Jellyfin's `/health` and MediaManager's `/api/v1/health` (`nas_proxy_health_checks`) and pushes ONE result (up when every app answers, else down with curl's error of each failing app) through `uptime-push` (role `uptime_push`, a `meta` dependency) to the single `Healthcheck NAS` monitor (`uptimekuma_monitor_push.health_nas`, `tofu/pangolin_config/health_nas.tf`: a 10 min window and one 5 min retry, so two failed checks in a row page, a silent NAS pages after 15 min). The push URL (`uptime_health_nas_url`, read by `nas.yml` into `nas_proxy_healthcheck_url`) lives in `health/nas.curl`, `0600` root, `no_log`; an empty one removes that file and the apps are checked without pushing (the former `health/jellyfin.curl` and `health/mediamanager.curl` are removed). `https://media.sylvain.cloud` (Jellyfin), `https://nas.sylvain.cloud` (UGOS's UI, `http://<NAS LAN IP>:9999` behind it) and `https://mediamanager.sylvain.cloud` (MediaManager trial, `http://mediamanager:8000` on the internal `mediamanager_proxy` network that `dc@nas_proxy` creates and `dc@mediamanager` joins as external, hence `mediamanager` after `nas_proxy` in `nas.yml`: the trial depends on the proxy, never the other way round, so removing it or a failed `dc@mediamanager` never takes `media`/`nas.sylvain.cloud` down), with or without `:8443`, at home and through the Pangolin client (public A records `tofu/dns/media.tf`/`nas.tf`/`mediamanager.tf` to the NAS's LAN IP, beating the `*.sylvain.cloud` wildcard, each in Blocky's `blocky_rebinding_allowed_domains`; private resources `media.sylvain.cloud` and `mediamanager.sylvain.cloud`, site `nas`, `nas-proxy` on the `newt` network, TCP 443 and 8443, and `nas`, site `proxmox-lxc`, LAN IP, TCP 22, 443, 445, 8443, 9999). Jellyfin's and MediaManager's routers have no source filter: both Pangolin resources reach the same `nas-proxy` ports, so a `jellyfin` role member can reach MediaManager's login page by asking for its name (and the other way round), like any LAN device; each app's own account is the gate. `https://prowlarr.sylvain.cloud` and `https://qbittorrent.sylvain.cloud` (MediaManager's tools, `http://mediamanager-gluetun:9696` and `:8080`: gluetun joins `mediamanager_proxy` too, its firewall lets the network's subnet in and nothing else out) work the same way, with their own routers, A records (`tofu/dns/prowlarr.tf`, `qbittorrent.tf`), Blocky entries, certificate-check names and private Pangolin resources, bound to the role `mediamanager-admin` only; not in `nas_proxy_health_checks` (their containers exist only once the VPN key is set). **Pocket ID in front of Prowlarr and qBittorrent**: when the Tofu outputs `pocket_id_mediamanager_tools_client_id`/`_client_secret` and `pocket_id_issuer` exist (client `mediamanager-tools`, `tofu/pangolin_config/pocket_id.tf`; read in `defaults/main.yml`, nothing rendered otherwise), the compose gets a third service `oauth2-proxy` (container `nas-proxy-oauth2`, `quay.io/oauth2-proxy/oauth2-proxy` pinned by tag and digest, distroless, non-root, `cap_drop: ALL`, read-only, `newt` network only so it reaches `id.sylvain.cloud` by the NAS's normal egress and never through gluetun, no published port, no healthcheck: no shell in the image; `mem_limit` 64m is an estimate, ~2x a Go proxy's 15 to 30 MB RSS, to be re-set on `memory.peak`). The `prowlarr` and `qbittorrent` routers get `[oauth2-signin, oauth2-auth, mediamanager-headers]`: `oauth2-auth` is a forwardAuth to `/oauth2/auth` (202 with a valid session of group `mediamanager-admin`, else 401), `oauth2-signin` an errors middleware (outermost) that replaces that 401 with oauth2-proxy's `/oauth2/sign_in?rd={url}` page (Traefik's `{url}` is the full, escaped original URL, hence `--whitelist-domain` for both names with any port), whose button goes to Pocket ID. A router per name, `<name>-oauth2` (`Host && PathPrefix(/oauth2/)`, priority 1000), sends `/oauth2/` (start, callback) to oauth2-proxy; the callback comes from `X-Forwarded-Host/-Proto` (`--reverse-proxy`), so 443 and 8443 are both registered in the Pocket ID client. One session cookie per name (`__Host-oauth2`: Secure, Path=/, no Domain, never `.sylvain.cloud`); cookie secret = 32 hex characters derived from `backup_passphrase` (no SOPS key). PKCE S256, `--allowed-group=mediamanager-admin` on the `groups` claim, plus the client's own `allowed_user_groups` (double gate). The `mediamanager`, `media` and `nas` routers are untouched. The apps' own logins stay. Break glass if Pocket ID or the proxy is down (Traefik then fails closed: 5xx, or a sign-in page that cannot finish): SSH tunnel to the NAS's `127.0.0.1:8080` / `9696` (published by gluetun, bypasses Traefik; `ansible/roles/mediamanager/README.md`). A backend's own 401 is also replaced by the sign-in page (errors middleware); Prowlarr and qBittorrent answer 302/403 to their logins, and MediaManager reaches them on the internal network, not through Traefik. Only `ugos` is LAN-only (`ugos-lan`). `8443` is published by Docker on `nas-proxy`. The host's `443` is **not** published: it is held by a second service of the same compose, `forward` (container `nas-proxy-443`, same Traefik image, `network_mode: host`, TCP passthrough to `nas-proxy`'s unpublished `websecure-forwarded` entrypoint `172.30.96.10:8444` with PROXY protocol v2, trusted from the host's `jellyfin_media` gateway `172.30.96.1` only, so `ugos-lan` and Jellyfin still see the client IP). Port 443 is free only while UGOS's "redirect HTTP/HTTPS to the UI's HTTPS port" setting is unticked (`defaultHttpsRedirectEnable` in `/etc/nginx/config.json`, a 307 to `:9443` in `ugreen_ssl_redirect.conf`); if a UGOS update ticks it again and nginx starts first, the relay's Traefik exits on bind and Docker retries it (back-off up to 1 min) while `nas-proxy` and `:8443` keep running (nothing orders nginx before Docker: if the relay holds 443 first, nginx fails and the whole UGOS UI with it; `docker stop nas-proxy-443`, restart nginx, untick, `docker start nas-proxy-443`) — a published 443 would instead fail the container create, hence `up`, and `dc@`'s `ExecStop` would stop `nas-proxy` on every retry. The role flushes its handlers then fails (`tasks/host_https_port.yml`, `ss -p`) when anything but the relay listens on the host's 443. Port 80 stays with UGOS's nginx (DNS-01 needs none).
