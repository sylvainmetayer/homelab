# Role `mem_report`

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

- Weekly container memory report (`mem_report` role, docker/pi/flip, outside Beszel): `mem-report.timer` (Monday 09:00) runs `files/mem_report.py` as `sylvain` + group `docker` (system unit, read-only sandbox), which reads each running container's cgroup v2 (`memory.max`/`peak`/`current`/`events`, scope found by walking `/sys/fs/cgroup` for `docker-<id>.scope`, so a `cgroup_parent` slice works too) and publishes one JSON message per host to ntfy's `/` on topic `scripts` (token `ntfy_scripts_token`, `0600` root `EnvironmentFile`): containers at ≥ 80 % of their limit or OOM-killed, those peaking under 25 % when the suggested limit frees ≥ 64 MiB, and those without a limit, each with a suggested `mem_limit` of 2× peak rounded up. `memory.peak`/`memory.events` reset with the cgroup (container or host restart): the message says so and flags a peak measured over < 7 days. Molecule `mem_report` runs it against a fake cgroup tree, a fake `docker` and a fake ntfy, runs the real `docker compose config` under the unit's sandbox, then starts the real unit.
- **Declared vs real limit**: the first section of the same report (priority 4). For each running container with Compose labels, the script reads `mem_limit` from `docker compose -f <config_files label> config --format json --no-interpolate --no-env-resolution` (kept in memory, never logged, its stderr neither) and compares it with `memory.max`, 64 KiB of tolerance for the kernel's page rounding. It catches what Compose cannot see: a container created without the memory controller keeps `max` once the controller is back (Docker dropped the limit at creation, `HostConfig.Memory = 0`), and `up` does not recreate it since its config hash has not changed. Hence the cgroup and not `HostConfig.Memory`: on a host without the controller the latter can say a limit that nothing applies; there, a declared limit is reported as « contrôleur mémoire absent ». A declared limit that is not applied replaces the « Sans limite » line. Fix: `docker compose up -d --force-recreate <service>` in the app's folder; a restart is not enough. A compose that cannot be read, within 60 s each and 3 min for the host (the unit is killed at 5 min), or a service gone from its compose (container left behind, `--force-recreate` would refuse it) is listed (« Limite non comparée », priority 3), never counted as compliant; nor is a container whose cgroup was not found. Not compared: stopped containers, containers without Compose labels, `deploy.resources.limits` (no compose here uses it, it would show as a false drift), and the hosts without this role (NAS, Pangolin).
