# Role `docker_service`

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

## The systemd pattern

Every containerized app runs as a **systemd user service** (a system service on the NAS, see below) via a shared template instantiated per-service:

- `docker_service` role installs a `dc@.service` systemd *user* unit template (`roles/docker_service/templates/dc@.service.j2`) to `~/.config/systemd/user/dc@.service`, and enables lingering for the user (so services survive logout).
- Each app's compose project lives at `{{ docker_base_path }}/<service>` (default `docker_base_path: /opt/apps`), and is started as `dc@<service>.service` (`WorkingDirectory={{ docker_base_path }}/%i`). The unit waits (bounded) for the Docker daemon, pulls only the images that are missing (`ExecStartPre=docker compose pull --policy missing`, so a failed download fails the start job and the Ansible restart handler), then runs `docker compose up --remove-orphans` with no `--pull`: each service's `pull_policy` (default `missing`) decides, so a registry outage at boot cannot stop an app whose image is already present (images are digest-pinned, Renovate bumps them). It restarts every 15 s without a permanent give-up (`StartLimitIntervalSec=0`) and without a `RestartSteps` back-off, whose counter only resets on a manual start or `reset-failed`. An instance that must follow a mutable tag sets `pull_policy: always` on that service (e.g. `flip_planning_image_pull_policy` for the Keycloak bench).
- App roles just template a `compose.yaml` into that directory and `systemd: name=dc@<service> scope=user state=started enabled=true`, notifying a `Restart <service>` handler on change.
- **System scope (the NAS only).** `docker_service_scope: system` (`host_vars/nas`; default `user`, whose rendered unit is byte-identical to before) installs the same template as `/etc/systemd/system/dc@.service` (root, `0644`), run as root: no lingering, no docker group (`sylvain` is not in it on UGOS and `/etc/group` belongs to UGOS). The base path is asserted, never created or chmod'ed (`docker_base_path: /volume1/docker`, the UGOS Docker app's shared folder, SMB-shared to `admin` with `skip smb perm`, so an admin SMB account could read or edit the root-run composes: risk accepted; each app dir is `0700` root). The unit is ordered `After=` `docker_service_system_after` (`docker_serv.service docker.service` on the NAS) without `Wants=`/`Requires=`: UGOS leaves `docker.service` disabled and its `docker_serv` activates `docker.socket` once `/volume1` (the `data-root`) is mounted, so pulling Docker in earlier would start it on the root overlay. `WantedBy=multi-user.target`. An app role on that host uses `scope: "{{ docker_service_scope }}"` with `become: "{{ docker_service_scope == 'system' }}"` (as the role's `Daemon reload` handler does: a bare `become: true` would run `systemctl --user` as root on a user-scope host) in its systemd tasks and handlers; the roles running there (`beszel_agent`, `newt`, `jellyfin`, and `decommission_app`; `nas_proxy` runs on the NAS only and asserts it) derive it in their `vars/main.yml` (`<role>_dc_scope`, `<role>_as_root`: root owns the project dir and the compose), and Molecule's `_shared/tasks/verify_app.yml` follows `docker_service_scope` too (root-owned compose, system unit). `nas.yml` gathers no facts: no `ansible_facts['user_uid']`…, a role reads the ids it needs with `getent` (`jellyfin`). Molecule: the `nas` scenario replays `nas.yml` and checks the unit (`systemd-analyze verify`, loaded properties); the `jellyfin` and `nas_proxy` scenarios reuse its prepare (fake `media` share, a `renderD128` node made with `mknod`).
