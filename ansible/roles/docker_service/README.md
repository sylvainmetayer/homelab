# Role `docker_service`

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

## The systemd pattern

Every containerized app runs as a **systemd user service** (a system service on the NAS, see below) via a shared template instantiated per-service:

- `docker_service` role installs a `dc@.service` systemd *user* unit template (`roles/docker_service/templates/dc@.service.j2`) to `~/.config/systemd/user/dc@.service`, and enables lingering for the user (so services survive logout).
- Each app's compose project lives at `{{ docker_base_path }}/<service>` (default `docker_base_path: /opt/apps`), and is started as `dc@<service>.service` (`WorkingDirectory={{ docker_base_path }}/%i`). The unit waits (bounded) for the Docker daemon, pulls only the images that are missing (`ExecStartPre=docker compose pull --policy missing`, so a failed download fails the start job and the Ansible restart handler), then runs `docker compose up --remove-orphans` with no `--pull`: each service's `pull_policy` (default `missing`) decides, so a registry outage at boot cannot stop an app whose image is already present (images are digest-pinned, Renovate bumps them). It restarts every 15 s without a permanent give-up (`StartLimitIntervalSec=0`) and without a `RestartSteps` back-off, whose counter only resets on a manual start or `reset-failed`. An instance that must follow a mutable tag sets `pull_policy: always` on that service (e.g. `flip_planning_image_pull_policy` for the Keycloak bench).
- **No container output in the journal.** `up` stays in the foreground (its lifecycle is the unit's: it returns when every container has stopped, `ExecStop` stops them), but its stdout and stderr (`2>&1`: `up` writes there the lines a container writes on its own stderr, e.g. homebox and homepage-*, 56 % of the user manager's journal entries on 2026-11-13) go through `grep -a --line-buffered -v -E '^[A-Za-z0-9][A-Za-z0-9_.-]* +[|]'` (`bash -c '… | grep …; exit "$${PIPESTATUS[0]}"'`, so the unit still gets `up`'s exit code). That drops the « container-1  | line » copies (~80 % of the docker VM's journal, ~50 KB/s of journald writes for ~250 B/s of text, `docs/conventions/resource-limits.md`), already kept by Docker's json-file driver and read there by `log_agent`, and keeps compose's own stdout lines (`Attaching to …`, `<container> exited with code N`, container created/started/stopped, pull and errors: none carries the prefix). The change reaches a unit at its next restart, not at the deploy. Rejected: `--no-attach` on every service (`up` returns as soon as the *attached* containers stop, and excluding all of them attaches all), `--no-log-prefix` (same volume), `LogFilterPatterns=` (no effect in a user unit, and the NAS's systemd 252 predates it), `StandardOutput=null` (hides `exited with code`). Read a container's output with `docker logs <container>` (or VictoriaLogs), not `journalctl -u dc@<service>`. Molecule (`docker_service`) runs the unit's exact `ExecStart` under systemd with a fake `up` and asserts the kept lines and the exit code.
- App roles just template a `compose.yaml` into that directory and `systemd: name=dc@<service> scope=user state=started enabled=true`, notifying a `Restart <service>` handler on change.
- **System scope (the NAS only).** `docker_service_scope: system` (`host_vars/nas`; default `user`, whose rendered unit is byte-identical to before) installs the same template as `/etc/systemd/system/dc@.service` (root, `0644`), run as root: no lingering, no docker group (`sylvain` is not in it on UGOS and `/etc/group` belongs to UGOS). The base path is asserted, never created or chmod'ed (`docker_base_path: /volume1/docker`, the UGOS Docker app's shared folder, SMB-shared to `admin` with `skip smb perm`, so an admin SMB account could read or edit the root-run composes: risk accepted; each app dir is `0700` root). The unit is ordered `After=` `docker_service_system_after` (`docker_serv.service docker.service` on the NAS) without `Wants=`/`Requires=`: UGOS leaves `docker.service` disabled and its `docker_serv` activates `docker.socket` once `/volume1` (the `data-root`) is mounted, so pulling Docker in earlier would start it on the root overlay. `WantedBy=multi-user.target`. An app role on that host uses `scope: "{{ docker_service_scope }}"` with `become: "{{ docker_service_scope == 'system' }}"` (as the role's `Daemon reload` handler does: a bare `become: true` would run `systemctl --user` as root on a user-scope host) in its systemd tasks and handlers; the roles running there (`beszel_agent`, `log_agent`, `newt`, `jellyfin`, `immich_ml`, `mediamanager`, and `decommission_app`; `nas_proxy` runs on the NAS only and asserts it) derive it in their `vars/main.yml` (`<role>_dc_scope`, `<role>_as_root`: root owns the project dir and the compose), and Molecule's `_shared/tasks/verify_app.yml` follows `docker_service_scope` too (root-owned compose, system unit). `nas.yml` gathers no facts: no `ansible_facts['user_uid']`…, a role reads the ids it needs with `getent` (`jellyfin`). Molecule: the `nas` scenario replays `nas.yml` and checks the unit (`systemd-analyze verify`, loaded properties); the `jellyfin` and `nas_proxy` scenarios reuse its prepare (fake `media` share, a `renderD128` node made with `mknod`).
- **Docker log rotation on the NAS.** UGOS's Docker has no `json-file` rotation (`geerlingguy.docker` sets it elsewhere), so every compose of a role that runs there (`jellyfin`, `mediamanager`, `immich_ml`, `newt`, `log_agent`, `beszel_agent`, like `nas_proxy` and `kdrive_sync`) carries `logging: json-file, max-size 10m, max-file 3` on each service when `<role>_dc_scope` is `system`; the rendering on the user-scope hosts is unchanged. A changed `logging` recreates the containers at the next restart of the unit.

## Weekly removal of unused images

On user-scope hosts (docker, pi, flip), the role also installs `docker-image-prune.service` + `.timer` as **user** units next to `dc@.service` (`sylvain` is in the docker group). Every Sunday at 04:30 (`docker_service_image_prune_schedule`, `RandomizedDelaySec=15min`, `Persistent=true`: after borgmatic at 02:30, before the 05:00/05:30 kernel-update reboots) it runs exactly:

```
/usr/bin/docker image prune --all --force --filter until=168h
```

- `--all` removes every image **no container uses, running or stopped**, dangling or tagged. Never volumes, containers, networks or build cache (no `system prune`, no `--volumes`). A paused app keeps its images: `dc@` stops with `docker compose stop`, its containers stay.
- `until=` (`docker_service_image_prune_until`, default `168h`) filters on the image's **creation** (build) time, not on its last use: it only spares images *built* less than 7 days ago. An older upstream image goes at the first run after its last container is removed (a Renovate bump, a decommissioned app).
- What goes is what Renovate's digest bumps left behind: the next `dc@` start of the app only pulls what is missing, and an app whose image was removed under it (only possible if its container was deleted too) re-pulls it on start.
- Output (deleted images, `Total reclaimed space`) goes to the user journal: `journalctl --user -u docker-image-prune`. No ntfy message.
- Before pruning, the service waits (120 s at most) for the Docker daemon, as `dc@` does: a user unit cannot be ordered after `docker.service`, and the `Persistent=true` catch-up of a missed week fires at boot.
- `docker_service_image_prune_enabled: false` stops and disables the timer and removes both units. Not installed in system scope: the NAS, whose UGOS Docker app manages its own projects, is pruned by hand if ever needed. Not on Pangolin either, which has no `docker_service` (its compose runs outside `dc@`, and geoipupdate's `docker run --rm` image would be deleted every week): prune it by hand (`docker image prune -a`) after Pangolin image bumps.
- Molecule (`docker_service`) asserts the exact `ExecStart` and the Docker wait, that no volume/system/builder prune appears, that the timer is enabled and active, and runs the service once against the test container's Docker daemon; the `nas` scenario asserts no prune unit is written there.
