## Monitoring (hub and agents)

The agent role is `beszel_agent`, whose README points here.

- Monitoring is Beszel (`docs/architecture.md`, « La supervision »): hub role `beszel` on the Docker VM, agent role `beszel_agent` on every host (`dc@beszel_agent` on docker/pi/flip, the same mode `dc` on the NAS, where `docker_service_scope: system` makes it a root system unit under `docker_base_path`, `docker compose up -d` on Pangolin, a systemd binary on the newt LXC and on the Proxmox host, `pve.yml`, which also reads S.M.A.R.T.). Agents dial the hub (no listening port): LAN hosts on `192.168.1.216:8090` (published by Docker, so before ufw: only the Beszel account guards the UI there), Pangolin and flip through the public resource's `/api/beszel/agent-connect` PASS with a per-agent Pangolin access token (`beszel_agent_hub_headers` output). The hub's `config.yml` is authoritative: a host removed from the SOPS dict `beszel_agent_tokens` loses its history. It only knows systems: alerts (`beszel_alerts`) and the Telegram/e-mail channels (`user_settings`; e-mail through the SMTP set in the hub's UI; Telegram only once the optional SOPS keys `beszel_telegram_bot_token`/`beszel_telegram_chat_id` exist, which they do not today) are written by the role through the hub API at `127.0.0.1:8090`, logged in as the admin account (so `beszel_admin_password` must stay its password), authoritative too (tag `beszel_alerts`; test message: `--tags beszel_alerts_test`). The agent never mounts the Docker socket: a `wollomatic/socket-proxy` sidecar (GET-only allowlist `beszel_agent_socket_proxy_allow_get`: container logs by hex ID yes, inspect no — Beszel strips only `Config.Env` from it, command args and labels would pass) does. The hub's `CONTAINER_DETAILS=true` serves the UI's container sheet, logs relayed on demand (last 200 lines, never stored) to any Beszel account with access to the system; its inspect pane stays empty (403 at each agent's proxy, logged on every sheet opening). Binary-mode hosts (newt LXC, pve) have no Docker, hence no container sheet, and no systemd service logs either: their unit's `DynamicUser` is in no journal group, so the agent finds the system journal unreadable and turns them off (`SupplementaryGroups=systemd-journal` would open the whole journal, not just `SERVICE_PATTERNS`).
