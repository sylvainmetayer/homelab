## Widgets

- Homepage widgets (`ansible/roles/homepage`, `services.yaml`, queried server-side): Beszel on its link (widget version 2 logs in as a PocketBase **superuser**, so a dedicated one, `beszel_homepage_email` in `host_vars/docker`, SOPS `homepage_beszel_password`, created or reset by the `beszel` role with `docker exec beszel /beszel superuser upsert` whenever its password is refused (400) — Molecule swaps in `beszel_superuser_command`; accepted risk: that superuser can read and write the whole hub, so whoever reads Homepage's config owns Beszel). The hub has PocketBase `superuserIPs` set (in the UI: one public IP, plus `172.16.97.3` since 2026-10-29): a superuser with the right password from any other source gets 403 « You are not allowed to perform this request. », so Homepage reaches the hub over its own internal network `beszel_homepage` (fixed subnet and IPs in `host_vars/docker`, created by `dc@beszel`, joined as external by Homepage; the widget URL is the hub's IP there, not its name) and its fixed IP `beszel_homepage_client_ip` must be added to that list by hand. The account step never fails the play: 403 counts as a valid account (from the host the source is the Docker gateway), any other failure warns and sets `beszel_homepage_account_ready: false`, which drops the widget for that run. On since 2026-10-29 (`beszel_homepage_email: ""` turns it off; steps both ways in `docs/architecture.md`, « La supervision »), and one Uptime Kuma card per published status page of `homepage_uptimekuma_status_pages` — only `sylvain-dev` (slug pinned by the `homepage_status_pages_match_the_role` test): the backups get no public status page, by decision. URL from the `homepage_uptimekuma_url` output (`status_page_site.tf`) read by `docker.yml`. Either half is skipped when its credential or URL is empty. Also: header widgets (search, datetime, Open-Meteo), a `siteMonitor` dot on every link whose internal address is known (`internal_url`/`site_monitor` fields of `homepage_links`: Pangolin's target and probe path, Docker VM targets only; LAN IPs set in the role for the Pi's Immich, Jellyfin, Proxmox; none for flip), one Beszel card per `beszel_agent_tokens` key (group Hôtes, `systemId`), and `homepage_link_widgets_extra` (Proxmox, Pangolin with the `homepage_pangolin_org` output, Speedtest Tracker, Immich, Jellyfin, Homebox, Karakeep) plus an iCal agenda card (calendars Perso and Top nous, `homepage_calendars`, one integration per non-empty key, read through `ical-filter`, below), each rendered only when its optional SOPS key `homepage_*` is non-empty (role defaults read them with `| default('')`; Molecule renders the config both with and without them). Jellyfin/Homebox/Karakeep credentials are not read-only: accepted risk (Sylvain, 2026-10-29, `docs/architecture.md`). Token creation: `docs/runbooks/rotation-des-secrets.md#widgets-de-homepage`.

- Supervision group (after Administration), three read-only cards, each rendered only with its optional SOPS key (Molecule renders with both, with none, and with the vmauth one only):
  - **Sondes en panne** and **Sauvegardes** (SOPS `homepage_uptimekuma_api_key`, plus the `homepage_uptimekuma_url` output): no status page, since one is public by nature and the backups get none, by decision; Uptime Kuma has no read-only account and no REST API. Its `/metrics` (Prometheus) is behind an API key that opens nothing else (Uptime Kuma 2.x `apiAuth`, 60 requests a minute). Homepage cannot read that format, so `kuma-summary` (below) reads it and serves JSON to two `customapi` `dynamic-list` cards: the monitors whose `monitor_status` is 0 (no `group` folders, which double their monitors; paused monitors are absent from `/metrics`), or a single « Toutes les sondes » line; and every `push` monitor named `Backup <app>`, « OK » / « En retard » / « En attente » / « Maintenance », late ones first. `/metrics` has no heartbeat time: « OK » means pushed within the 25 h window (`backup_push_interval`), not a timestamp — the time of the last push would need the status-page heartbeat API (public) or a socket.io login with the admin account, both rejected.
  - **CrowdSec** (SOPS `homepage_victoria_logs_password`): not the `crowdsec` widget, which logs into the LAPI as a machine (a watcher can write alerts and delete decisions) and would need the LAPI, on Pangolin, published on the Internet. Pangolin's Vector already ships CrowdSec's lines to VictoriaLogs on this VM, with the `crowdsec` (`alert`/`decision`), `decision` and `client_ip` fields (`log_agent`). The card is a `customapi` on vmauth over newt (`victoria-logs-auth:8427`) with the `homepage` account the `victoria_logs` role creates from the same key: route `/select/logsql/stats_query` only, `extra_stream_filters={host="pangolin",container="crowdsec"}` set by vmauth, which a client cannot override (checked on vmauth 1.155 / VictoriaLogs 1.53: a client `extra_stream_filters` is ignored, `/select/logsql/query` refused). Worst case, whoever reads Homepage's config reads CrowdSec's log lines (attackers' IPs and scenarios) through `stats by (_msg)`. Two numbers: alerts over 24 h, distinct IPs banned over 4 h (the default profile's ban: the bans in force); neither the community blocklist nor AppSec alert-only hits. The LogsQL query is fully URL-encoded: Homepage substitutes any `{…}` of a widget URL. Refresh every 5 min.
- Host cards: `highlight` on Beszel's `disk` field, red from 80 % (`homepage_beszel_host_highlight`; Homepage block highlighting, read in the v2.7.0 source, not available on `customapi`). On the NAS that disk is `/volume1`: the agent runs in a container, and the root it measures is Docker's, `/volume1/@docker` (checked 2026-11-01: `/` in the agent container and `/volume1` on the host both 24 %). No new Beszel login (PocketBase allows 2 auths per 3 s per IP, one per card).

## Uptime Kuma summary (`kuma-summary`)

Second helper service of the compose project, same pattern as `ical-filter` (`files/kuma_summary.py`, standard library only, same pinned `python:*-alpine` image): reads `<homepage_uptimekuma_url>/metrics` with the API key (Basic auth, the key as password), at most once per `homepage_kuma_summary_cache_seconds` (60; a stale copy is served while Uptime Kuma fails, 502 without any), keeps only each monitor's name, type and `monitor_status`, and serves `/down.json` and `/backups.json` at `http://kuma-summary:8080`; `/healthz` answers without touching Uptime Kuma.

- The key (`KUMA_API_KEY`) lives in `compose.yaml` (0600, `diff: false`) only, never in `services.yaml`; error replies name neither the URL nor the key.
- Network: `kuma`, the project's own network, joined by Homepage; no published port; egress to PikaPods (https only, no redirect followed: urllib would resend the key to the target).
- Hardening and memory as `ical-filter` (`nobody`, `read_only`, `cap_drop: ALL`, `mem_limit: 64m`, not measured yet). `/metrics` above 8 MiB is refused.
- No key or no URL: no service, no `kuma` network, no cards.
- Tests: `ansible/molecule/homepage/files/test_kuma_summary.py`, run by `verify.yml` with `test_ical_filter.py`. Debug: `python3 kuma_summary.py --parse < metrics.txt`.

## Calendar filter (`ical-filter`)

Homepage's `calendar` widget shows every VTODO as an event dated « now »: the shared Nextcloud calendar Top nous has dozens of tasks, which hid the real events. Homepage therefore never reads the share URLs. A second service of the same compose project, `ical-filter` (`files/ical_filter.py`, Python standard library only, on the pinned `python:*-alpine` image), fetches each calendar of `homepage_calendars` whose SOPS key is non-empty, drops its VTODO and VJOURNAL components (nested VALARM included; everything else, folded lines and line endings, is copied byte for byte), keeps the result `homepage_ical_filter_cache_seconds` (300; a stale copy is served while the upstream fails, 502 without any copy) and serves it at `http://ical-filter:8080/<slug>.ics`. Homepage's integrations point there; `/healthz` answers without touching the calendars.

- The share URLs (`ICAL_FEED_<SLUG>`, `https://` only, never logged) live in `compose.yaml` (0600, `diff: false`) only, not in `services.yaml`.
- Network: `ical`, the project's own network (not `external`), which Homepage joins too; not `newt` (Pangolin has nothing to reach there), no published port. It needs egress: the share URLs go through Pangolin like any public client.
- Hardening: `nobody` (65534), `read_only`, `cap_drop: ALL`, `no-new-privileges`, the script its only (read-only) mount, hence 0644 on the host. `mem_limit: 64m`, not measured yet: re-check `memory.peak` in the Monday `mem_report`. An upstream calendar larger than 2 MiB is refused (two at the cap stay well under 64m).
- No calendar key: no `ical-filter` service, no `ical` network.
- Tests: `ansible/molecule/homepage/files/test_ical_filter.py` (filter, cache, HTTP server), run by the scenario's `verify.yml` with the test host's `python3` (Molecule starts no container); by hand, copy it next to `ical_filter.py` and run `python3 -I -m unittest discover -s . -p 'test_*.py'`. Debug on the host: `python3 ical_filter.py --filter < calendar.ics`.
