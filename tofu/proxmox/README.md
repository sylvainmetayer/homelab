# tofu/proxmox

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

`tofu/proxmox/` — Proxmox VE provider: the Docker VM (`proxmox_docker_vm.tf`, read back as inventory by `ansible/inventory/proxmox.py`) and the Newt LXC container (`proxmox_newt_lxc.tf`; static in `inventory/hosts`, configured by `ansible/lxc.yml`), and their nightly vzdump job (`backup.tf`: `proxmox_backup_job`, imported from the job created in the UI) onto the NFS storage `nas-backup` (export `/volume1/pve-backup` of `host_vars/nas`, client the Proxmox host only; the test pins that contract), never onto `local`, the host's root.

The provider never stops the Docker VM to apply an **update**: `reboot_after_update = false` (its default, `true`, would shut the VM down and start it again, every app with it, to apply a change that needs it). A change Proxmox cannot hotplug (a serial port, the CPU type, cores, memory…) is written to the VM config as **pending**, the apply ends with the warning « a reboot is required … Please reboot the VM manually », and it takes effect at the next **cold start** of the VM: by hand on the Proxmox host, `qm shutdown 100 --timeout 300 && qm start 100`, or unannounced at the next host reboot (`docs/runbooks/mises-a-jour-proxmox-ugos.md`). A reboot from inside the guest (unattended-upgrades at 05:00) keeps the same QEMU process, hence the old hardware. `tofu plan` cannot see what waits (the provider reads the config with its pending values applied, so the next plan is empty): `qm pending 100` lists it. A disk resize alone is applied online (disks are hotpluggable). Moving a disk to another datastore, or a resize in the same apply as a pending change, fails the apply instead of powering the VM off; in the latter case the other changes were already written as pending, and the next apply only retries the disk. The flag does not cover a **replacement**: a ForceNew change (the cloud-init `user_data_file_id`/`vendor_data_file_id`, which an edit of the snippets — `keys/perso.pub` included — makes unknown at plan time) destroys and recreates the VM, so read every plan for `must be replaced`. `serial_device` (`serial0`, a socket) backs the `console=ttyS0` of the Debian cloud image: without it, `serial-getty@ttyS0` failed every ~20 s. The default VGA display stays, so both the noVNC and the xterm.js consoles work (`qm terminal 100` too).

The Debian images (`debian_13` for the VM, `debian` for the LXC template) are `proxmox_download_file`, the name `bpg/proxmox` gives since 0.118 to `proxmox_virtual_environment_download_file` (deprecated, removed in 1.0). The state was carried over by `moved` blocks (the provider implements the cross-type move: plan « has moved », 0 to change, nothing downloaded again); they stay harmless once applied and can be dropped after every state has gone through them. A `moved` block is no `import` block: `tofu test` accepts it.
