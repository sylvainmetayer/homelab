- **SOPS files in CI** (ADR 0018): they live in the private `homelab-secrets` repository, mounted as the `secrets/` submodule. The jobs that read them (Lint's `Ansible lint`, `deploy-docker-app`, `secrets-rotation`) call `.github/actions/secrets-checkout` after the main checkout: it reads the commit the submodule pins (`git ls-tree HEAD secrets`) and checks it out into `secrets/` with the read-only deploy key `HOMELAB_SECRETS_SSH_KEY`, a **repository** secret (`tofu/github/repository_homelab_secrets.tf`; an environment is main-only and Lint runs on PRs), credentials not persisted. A fork PR gets no secret, so its `Ansible lint` fails. Tests (Molecule on `fake_secrets.yml`, `tofu test` on `override_data`) never clone it; `select_tests.py` classifies a submodule bump (`secrets`) as test-free.
- `.github/workflows/lint.yaml`, job `CI lint` — zizmor (actions pinned by SHA, template injection, persisted checkout credentials), actionlint (`.github/actionlint.yaml` declares the `ubuntu-26.04` label) and hadolint on the Molecule Dockerfile (`.hadolint.yaml`), all as pinned binaries checked by sha256. Locally: `mise run lint-ci`. Their versions (and Trivy's, sops's, `uv==` of the workflows, kept equal to `mise.toml`'s) are followed by Renovate regex managers on a `# renovate:` comment: a bump changes the version only, its sha256 is redone by hand on the PR branch (zizmor has none: uvx installs it from PyPI). The OpenTofu version of every job is read from `mise.toml`, and the modules require `~> 1.13`. Every `actions/checkout` sets `persist-credentials: false`; a matrix value reaches a `run:` through `env:`, never as `${{ … }}` inside the script. Secrets: `mise run secrets-scan` (gitleaks over the whole history, `.gitleaks.toml` lists each known false positive with its reason; no `*.sops.yaml` is allowlisted, Lint fails on a SOPS file tracked outside the `secrets/` submodule. GitGuardian covers the PRs, gitleaks is not a CI job) and `mise run install-hooks` (gitleaks pre-commit hook on staged changes).
- `.github/workflows/lint.yaml`, step `Verify the actions lock` of the `CI lint` job, and `.github/workflows/actions.lock` (ADR 0036) — every `uses:` stays pinned by SHA with its version in a comment, **and** the lock written by the `gh actions-lock` extension (pinned `v0.4.1` by `GH_ACTIONS_LOCK_VERSION` of `lint.yaml`, which Renovate follows without automerge; the extension is installed by tag, not by sha256 like the other CI lint tools) records each action's commit. What it guarantees: the runner re-reads the lock at job start and refuses a job whose action has no entry, a commit that left the upstream history, or a repository now owned by someone else under the same name; `--verify` (a step of `CI lint`, so on every PR and on pushes to `main` touching `.github/**`, `contents: read`; a step and not a workflow of its own because `CI lint` is a required check of the `main` ruleset and an automerged Renovate PR must wait for it) fails when the lock no longer follows the `uses:` or a locked pin no longer checks upstream. What it does not cover: the 7 local `./.github/actions/*` uses (kept in `./`, `--ignore-local-actions`: actionlint 1.7.12 rejects the `$/` form that would lock them; the `actions/checkout` of `secrets-checkout` is in the lock only because each caller uses the same SHA directly, and `--verify` does not check that, upstream issue #281, so bump a composite action's `uses:` and its callers together), reusable workflows of another repository (none here), container images (digest-pinned by hand, outside the lock), and a floating ref moved back to an older commit. Neither `sha_pinning_required` (`github_actions_repository_permissions` does not set it, live `false`) nor the org-level « Require lockfile » policy is needed (the tool left the workflows intact with the policy off, measured on v0.4.1). **Regenerate by hand** after adding a workflow or changing a `uses:` (Renovate does it itself for its bumps, on the same branch, with its own pinned extension: the lock regenerated by the command it runs was checked on a simulated bump, Renovate itself was not run; a stale lock fails `CI lint`, so the automerge waits): `gh extension install github/gh-actions-lock --pin v0.4.1`, then `gh actions-lock --ignore-local-actions --no-narrow` from the repository root, then read the diff of `actions.lock`: each entry must be `owner/repo@<sha of the uses:>`, a new action or a changed SHA is the only acceptable change. `--no-narrow` is what keeps the lock keyed by the SHA of the workflows (a plain run leaves the workflows alone here too, measured on v0.4.1 with the SHA policy off, but writes entries keyed `@v7.0.1`, which the workflows do not say; the warning « pinned to a bare SHA without a tag ref » is expected and does not fail). `--verify` needs no `--no-narrow`: it writes nothing. **When `--verify` fails**, read the category (`not-pinned`, `ref-changed`, `stale`: regenerate as above; `unreachable-pin`, `tag-commit-mismatch`, `repo-replaced`: an upstream tag was moved, a history rewritten or a repository replaced, which is the very thing the lock catches: read the upstream history first, never `--accept-moved` in automation, restore `actions.lock` from `origin/main` and keep the old SHA until the new commit is understood; `reachability-unknown`: GitHub did not answer, re-run). Never delete the lock to silence an error (every ref would be resolved again to whatever it points to today), never edit it by hand. A failing run of a job on `Missing pin for …`: the lock lacks the entry the runner expects (the SHA of a composite action's `uses:` not repeated in the calling workflow): add that action to the workflow's lock by regenerating, or key the entry by SHA. Troubleshooting of the tool: its `docs/troubleshooting.md`. zizmor 1.30.1 stays: SHA pins are kept, so `unpinned-uses` does not fire (checked with the lock present); a bump to 1.32 or later only becomes needed if the workflows move to tags (mode B of ADR 0036, rejected).
- `.github/workflows/deploy-docker-app.yaml` — on a push to `main` touching `ansible/roles/**`, a host playbook, `ansible/host_vars/<host>/` of a CI-deployed host (docker, pi, pangolin, flip), `ansible/group_vars/all/**`, `ansible/tasks/**`, `ansible/requirements.yml`, or the sources of the docs site (`docs/**`, `mkdocs.yml`, its scripts `.github/scripts/mkdocs_*.py`: `ROLE_SOURCES` maps them to the `docs_site` tag on docker) (or by hand, `workflow_dispatch` with forced `tags`), opens the OLM tunnel and runs the playbooks with the tags `resolve_docker_tags.py` derives from the changed files. A role's own `README.md` is skipped: documentation, never read by Ansible, it deploys nothing. A changed playbook is compared as YAML with the diff base (`--base`): the `roles:` entries added or changed (their `vars:`, e.g. one `flip_planning` instance) deploy their own tags (not one other entries share, like `monitoring`, when they have another), a comment or a removed entry deploys nothing, and anything else (pre_tasks, tasks, play keys, an untagged entry, no readable base) runs the whole playbook (`--tags all`, which still skips `never`). A `host_vars/<host>/` change runs that host's whole playbook (which role reads which variable is not derived; an idempotent run restarts nothing). A change to a file every playbook reads, `ansible/group_vars/all/**`, `ansible/tasks/**` (the shared pre_tasks, `pangolin_config_outputs.yml`) or `ansible/requirements.yml` (galaxy roles and collections), runs all four playbooks whole: heavy, but no change is lost. Left out on purpose: a bump of the `secrets/` submodule (a rotation is applied by hand, in the runbook's order), and the files that change no host: `ansible.cfg`, `known_hosts`, `inventory/` (the CI writes its own `ci-inventory.ini`), `ansible/mise.toml`, `molecule/`, `uv.lock`. The YAML is compared net from the base: a revert of a half-applied playbook change deploys nothing, re-run it by hand. Runs are serialized (`concurrency: deploy-docker-app`, OLM refuses a second connection), and bounded: `timeout-minutes` 120 on `deploy` (58 min measured with the four hosts), 10 on `window`, and `Deploy pi` stops waiting when the background process is gone without an exit code, and GitHub keeps one **pending** run per group: a third push cancels the pending one. So the changed files are diffed from the head of the **last successful push or schedule run** (read through the API, `actions: read`), not from the push's own `before`: the next run catches up a cancelled or failed one, a run failing halfway is retried whole (idempotent), dispatch runs never count as a base, a re-run of a commit older than that base deploys nothing (it would roll back), and an API error fails the run rather than deploy only the push. The files are those of every commit of the range plus the net diff (a revert of a half-applied commit nets to nothing), and each host's `Deploy <host>` step runs even when an earlier one failed (`!cancelled()`), or a host that stays down would block the others in every run. **Order**: `docker` and `pi` run at once (a step `Start the pi deploy in the background` launches pi, its exit code and log go to `$RUNNER_TEMP`, then `Deploy docker` runs live and `Deploy pi` waits for pi, prints its buffered log and fails with its code), then `pangolin`, then `flip`, alone and in sequence (58 min when the four ran one after the other, 2026-11-09). `pangolin` never runs alongside another play: it is the OLM server and flip's ProxyJump, and its handlers (sshd, ufw, fail2ban, nat-gateway, docker, the Pangolin stack) would cut the tunnel or the jump under a play still running; `flip` waits for it for the same reason. The `Deploy <host>` step names are read by `ci_key_audit` (jobs API): keep them. One job and one OLM tunnel stay (a second client with the same credential is refused). **Quiet window** (ADR 0029): an automatic run (push or `schedule`) that starts between 19:00 and 08:00 Europe/Paris, every day, weekend included, is cancelled by its first job `window` (`.github/scripts/deploy_window.py`, `gh run cancel`, `actions: write` on that job only). It must be a cancel, not a skipped `deploy` job: that run would end green, become the « last successful run » and lose its commits. A cancelled run is never a base, so the first run inside the window deploys everything since the last success: the `schedule` crons (`0 6,7,9 * * *` UTC, i.e. 08:00 Paris in summer and in winter, the 09:00 one a net if GitHub delays or drops one; a schedule is never guaranteed to the minute) run the same catch-up, which does nothing when main is already deployed. The window is judged when the run starts, not at the push: a run queued behind a long one and starting at 19:05 is cancelled, one started at 18:59 finishes. A `workflow_dispatch` is always immediate: the exception for an urgent fix. Without `tags` it catches main up exactly like a `schedule` run (base = head of the last successful push or schedule run, nothing when main is already deployed; the `playbook` choice still narrows it); with `tags` it forces them and skips the detection. Renovate is unaffected (its PRs merge whenever, the deploy waits for the morning; the weekly digest counts failed runs only, a cancelled one is not). The crons are checked against the window every day of 2026-2031 by `test_deploy_window.py`. GitHub disables schedules of a public repository after 60 days without activity: the first push or a manual dispatch brings them back. The playbooks read the outputs of `tofu/pangolin_config` with `tofu output -json`: when a host is deployed, the workflow installs the OpenTofu version of `mise.toml`, fetches the provider fork (`fetch_pangolin_provider.sh`) and runs `tofu -chdir=tofu/pangolin_config init -lockfile=readonly` with the S3 read-only keys and the state passphrase (`tofu_state_passphrase`, dedicated to this state, which `init` needs to validate the encryption block; both decrypted from `ansible.sops.yaml` and masked; step « Init tofu/pangolin_config to read its outputs », before the OLM tunnel); a failure there (registry, GitHub releases, S3) stops the run before any host is touched.

- `.github/workflows/test.yaml` — discovers `ansible/molecule/*/molecule.yml` and `tofu/*/tests/` and runs one matrix job per tested Tofu module and one per **shard** of Molecule scenarios (`discover` splits the selection round-robin into at most 8 shards; a shard installs its environment once then runs its scenarios one after the other, a failing scenario does not stop the others, the failed ones are listed in the job summary and the job fails at the end) (see `docs/conventions/tests.md`). On a PR, only the suites the changed files reach (`.github/scripts/select_tests.py`, read from the tree: a scenario's roles followed through meta dependencies and `include_role`/`import_role`, the paths its files reach — host_vars, another scenario, a playbook —, a module's `file()`/`fileset()` reads; `ansible/molecule/_shared/vars/fake_secrets.yml` and `group_vars/**/*.yml` are compared key by key with the PR's base (`HEAD^1`) and rerun only the scenarios whose files (role, scenario, host_vars, shared tasks) mention an added or changed key, or a key whose value cites it (a removed or renamed key, an unreadable base or a file that is no mapping reruns every scenario; a key read through a name built at runtime is missed, the weekly run catches it); any other `_shared` file, `requirements.yml`, `uv.lock` rerun every scenario, `mise.toml` every module, `test.yaml` or the script everything, an unclassified file everything, docs nothing); a `full-tests` label, `workflow_dispatch` and the weekly run (Monday 03:30 UTC, `schedule`; no `push` trigger) run the full matrix. A dependency the script cannot read (a path built at runtime) is missed on the PR and caught by the weekly run: teach it to `select_tests.py`. The Molecule image is published on GHCR (`ghcr.io/sylvainmetayer/homelab-molecule:<hash of the Dockerfile>`) by `.github/workflows/molecule-image.yaml` (push to `main` touching the Dockerfile, Monday 03:00 UTC from scratch, by hand; the only workflow with `packages: write`, never from a PR); `discover` checks the tag exists and each Molecule shard pulls it and retags it `homelab-molecule:debian13`. Tag missing (a PR changing the Dockerfile, a fork PR with no read right on the package): the `Molecule image` job builds it once into the GitHub Actions cache (buildx, `type=gha`, scope = Dockerfile hash) and each shard loads it from there, as before. The Galaxy roles and collections (`ansible/galaxy_roles`, `ansible/collections`) are cached by `actions/cache` under the hash of `requirements.yml` (Tests and Lint's `Ansible lint`; the install step is skipped on a hit, main's weekly run seeds the cache for the PRs). `.venv` is not cached: `uv sync` takes 6 s. `Tests` stays the one required check, green when the matrices are empty. A new push to a PR cancels its running Tests and Lint runs (`concurrency`).

- `.github/workflows/codeql.yaml` — CodeQL in advanced setup (languages `actions` and `python`, build mode none, default query suite): weekly (Monday 04:30 UTC), by hand, and on the PRs and pushes to `main` touching `.github/scripts/**` or the workflow itself, not on every push/PR. - Renovate (`renovate.json`) automerges, through GitHub auto-merge once the `main` ruleset's four checks pass (so the merge deploys): our own images (`planning-equipes` patch/minor and the demo's main digest, `promptoramix`), and the Monday PR « weekly stateless automerged updates » — digest and patch updates of an **allowlist** of stateless images (no DB of their own, no data migration: homepage, karakeep-chrome, nginx-unprivileged (`docs_site`), and debian, the Molecule image's base; never rclone (kdrive_sync, NAS: `nas.yml` is run by hand, the merge deploys nothing, the bump would arrive unread), never in `ansible/roles/flip_planning/**`, whose restart takes the production planning and its Postgres along) and patch updates of GitHub Actions `uses:` (depType `action`; never their digest updates: a new digest under an unchanged tag is a moved tag, and an action runs next to the production secrets). Molecule pulls no image: a merged image that crashes leaves the deploy green and only its Uptime Kuma monitor tells; revert **and** drop it from the allowlist, or Renovate re-merges it the next Monday. Everything else (DB images, apps migrating their data or with a DB of their own, Traefik, the socket proxy, vmauth, the role groups, mise tools, minors and majors) stays manual. A paused app gets no PR at all (a « Paused apps » rule, `enabled: false` on the role's files and, if it has one, on its image in `path_bypass_images.json`, or the json alone would be bumped and fail `path_bypasses_follow_their_image`; none is needed today). Cadence (2026-10-29, after 152 Renovate PRs merged in 30 days): every third-party update waits `minimumReleaseAge: 3 days` (top level; images, GitHub Actions, mise tools, binaries; our own images and the Karakeep Button git ref, which has no release timestamp, reset it to `null`), so with the Monday window a release waits 3 to 10 days; digest/patch updates go to the Monday PR « weekly digest and patch updates » (manual) unless the stateless allowlist takes them, minor updates open on Monday only, one PR per package (manual, never automerged, not grouped: each app's data migration is read and deployed on its own), the `groupName` rules (beszel, vector, blocky, pangolin-role-dependencies, socket-proxy, borgmatic, immich-role-dependencies, enclosed) keeping their own PR on that same schedule; every major update gets no branch nor PR until its box is ticked in the Dependency Dashboard (issue #5, `dependencyDashboardApproval`); our own images (`planning-equipes`, `promptoramix`) are exempt from the delay, the window and the major approval (a planning-equipes major still opens its PR at once, merged by hand). `rebaseWhen: conflicted` is global: the `main` ruleset does not require an up-to-date branch (`strict_required_status_checks_policy = false`), so a PR is rebased only on a conflict (the default `auto` already did so for the manual PRs; the top-level setting extends it to every automerged one, our own images' included). The fast path for an image security fix is not Renovate (GitHub vulnerability alerts, which Renovate would follow without delay nor schedule, are off on this repo and cover no image anyway): the Monday `trivy.yaml` ntfy alert lists each fixable CRITICAL with its fixed version, bumped by hand or forced from the Dependency Dashboard. Renovate automerges a branch only if every update in it does: a group mixing both never automerges. Never add an image of `path_bypass_images.json` to the allowlist: its bump needs a human re-read of the public paths before the merge (the last `packageRules` entry sets `automerge: false` on that file as a guard, plus the PR note listing what to re-read).

- `.github/workflows/renovate-digest.yaml` — every Monday (13:00 UTC, after Renovate's morning run and the automerges it unlocks), `.github/scripts/renovate_digest.py` lists over 7 days the Renovate PRs merged (automerged, i.e. merged by Renovate itself, then by hand; repeated bumps of one package grouped as `xN`), the open Renovate PRs with their age (oldest first, auto-merge pending flagged) and the failed `deploy-docker-app.yaml` runs (a failure followed by a successful push run is marked caught up and no longer raises the priority), through the job's read-only `GITHUB_TOKEN` (GraphQL search + REST runs; `contents`, `pull-requests`, `actions: read`), and publishes it to ntfy's `/` on topic `github` with the `ntfy-github` environment's `NTFY_GITHUB_TOKEN` (`ntfy_github_token`: publisher `github` of the ntfy role, its own token, not the hosts' `scripts`). - `.github/workflows/trivy.yaml` — every Monday (05:00 UTC), Trivy scans every pinned image (`.github/scripts/trivy_images.py`, HIGH/CRITICAL with a fix only, `--ignore-unfixed`; one JSON report per image, converted to SARIF for code scanning) and the configuration.
