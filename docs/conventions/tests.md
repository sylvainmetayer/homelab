## Molecule

**Molecule** — one scenario per role, `ansible/molecule/<role>/` (scenario name = role name), run from `ansible/` (`molecule test -s <role>`). Exception: `security_flip` replays the `security` role with flip's host_vars (no SSH forwarding, private network never banned), sharing `security`'s prepare and verify tasks. The LAN hosts (docker VM, Pi) get no replay of their own: `security_lan` (`test_sequence: [converge]`, localhost, no container) only asserts the `security_*` values their host_vars hand the role (SSH and fail2ban whitelist on `192.168.1.0/24`, `vfat`, reboot times, the Pi's `vm.mmap_rnd_bits`).
- Shared base config: `.config/molecule/config.yml` at the repo root (auto-loaded): docker driver, image `homelab-molecule:debian13` built from `ansible/molecule/_shared/Dockerfile` (in CI pulled from GHCR, published by `molecule-image.yaml`, `docs/conventions/ci.md`) (Debian 13, systemd PID 1, Docker daemon, user `sylvain` with sudo — the playbooks' connection model), connection as `sylvain` with `XDG_RUNTIME_DIR` so `scope: user` tasks work.
- Shared prepare `ansible/molecule/_shared/prepare.yml`: linger, Docker + `newt` and `newt-public` networks, a `dc@.service` drop-in that runs `docker compose config --quiet` then sleeps (no image is ever pulled), a `/root/.local/bin/borgmatic` stub that validates each config with the real borgmatic baked into the image (version pinned in the Dockerfile, Renovate-tracked) and fakes `repo-create` exactly like borgmatic 2.x (exit 0, "Repository already exists. Skipping creation." on stdout at `--verbosity 1`). A scenario needing more imports it from its own `prepare.yml`.
- `converge.yml` loads `_shared/vars/fake_secrets.yml` through `_shared/tasks/load_fake_secrets.yml`, its first pre_task (`include_vars`: the same precedence layer as `community.sops.load_vars`, which a `vars_files` entry would not reproduce) (a dummy for every key of `secrets/ansible.sops.yaml` that a role reads — add new keys there; `host_user_password_hash`, read only by `00-setup.yaml`, is deliberately absent), `group_vars/all` and the **real** `host_vars/<host>` of the host running the role, then reproduces the playbook (roles before it, role-entry `vars:`, healthcheck `set_fact`s).
- `verify.yml` uses `_shared/tasks/verify_app.yml` for `dc@` apps plus role-specific assertions. Idempotence must hold.
- Never hardcode secret-looking literals in scenarios (GitGuardian fails the PR): compare against the fake-secret variables. Prefer 0700/0600 for files a prepare creates (SonarCloud).
- Molecule runs on `linear` (it reads no `ansible.cfg`). The production `mitogen_linear` strategy is exercised by Lint's `Mitogen strategy` job instead: `.github/mitogen-test/playbook.yml`, played from `ansible/` with the repository's `ansible.cfg` against two hosts in local connection (`hosts.ini`), with no container and no destroy. It runs the mechanisms Mitogen reimplements (template with `--diff`, copy, command loops, handlers, async, `delegate_to`, `set_fact` + `no_log`, `include_role`/`include_tasks`, `become` on the runner's passwordless sudo) and **fails if Mitogen is not the strategy** (the parent of a command's shell must be the process Mitogen renames `(mitogen:user@host:pid)`, not an AnsiballZ Python). About 1 minute with the setup, `timeout-minutes: 8` on the job and 3 on the step. It does not prove the ssh connection (`mitogen_ssh`, the Storage Box quirk of `backup.yaml`), `community.sops.load_vars` or a real host: for an ansible-core or Mitogen bump (Renovate's note) the manual `--check` on a host stays. Locally: from `ansible/`, `MITOGEN_TEST_DIR=<tmp dir> ansible-playbook -i ../.github/mitogen-test/hosts.ini --diff ../.github/mitogen-test/playbook.yml` (without `-e mitogen_test_become=true`, the `become` task is skipped). Do not replay a Molecule scenario under Mitogen: it hangs on the docker driver's `async_status` wait in Molecule's destroy playbook (PR #1374, the shard killed after 45 minutes).
- A new role gets a scenario: copy `ansible/molecule/trek/`. CI discovers it automatically.
- On a PR, a change to `fake_secrets.yml` or `group_vars` reruns only the scenarios that mention the added or changed keys (`select_tests.py`, keyed files): read a secret through its literal name in the role, scenario or host_vars, never a name built at runtime (`lookup('vars', prefix ~ ...)`), or only the weekly full run will catch a break.

## OpenTofu

**OpenTofu** — `tofu/<module>/tests/*.tftest.hcl`, run with `tofu init -backend=false && tofu test`: every provider is `mock_provider`, `sops_file` / `terraform_remote_state` / `http` data sources are `override_data`. Mostly `command = plan`; `apply` only where no `prevent_destroy` or provisioner exists. Some assertions read other repo files with `file()` (ansible inventory scripts, host_vars, playbooks) on purpose, to pin the Tofu ↔ Ansible contract. A module whose tests cannot run gets a `tests/.disabled` file stating why: CI discovery and `mise run tofu-test` skip it (CI prints the reason as a warning). An `import` block makes `tofu test` panic (OpenTofu refuses imports in a test context, mocked or not): `tofu/site` (2026-10-27) and `tofu/1y` (2026-10-29) only got their suites back once theirs, needed for the first apply only, was removed. An `import` block is therefore incompatible with `tofu test` — prefer the `tofu import` CLI command documented in the module's README, as `tofu/1y` already does for its DNS record. `keycloak_demo_planning_kc` vendors its `realm` module in `modules/realm/` (planning-equipes' `terraform/keycloak` at commit `bb374eac`, reachable from no branch or tag, so a `git::` source no longer initialised; only `tofu fmt` touched it): that module carries its own `provider "keycloak"` block, which `mock_provider` does not replace, so its tests `override_module` it (without it, the plan logs in to Keycloak), and a real `tofu plan` needs the demo's Keycloak up. CI uses the OpenTofu version pinned in `mise.toml`.
