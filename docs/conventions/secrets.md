# Secrets (SOPS + Age)

Moved from `AGENTS.md` (agent-facing notes, kept in English); the index there links here.

- **Where** (ADR 0018, `docs/adr/0018-secrets-depot-prive.md`): the SOPS files and the rotation inventory live in the **private** repository `sylvainmetayer/homelab-secrets` (`tofu/github/repository_homelab_secrets.tf`), mounted as the `secrets/` submodule (`.gitmodules`); `.sops.yaml` stays here. After a clone, and in every new worktree: `git submodule update --init` (without it, mise silently loads nothing, a Tofu `sops_file` and the playbooks fail on a missing file). Run sops from this repo (it finds `.sops.yaml` here; the private repo has none). A secret change is two commits: one in `secrets/`, pushed to `homelab-secrets`' `main` (no PR there: no CI, and no ruleset on a private repo of a Free account), then the submodule bump here (`git add secrets`) in a PR — CI reads only the commit this repo pins. Before editing: `git -C secrets switch main && git -C secrets pull --ff-only` (a freshly updated submodule is on a detached HEAD).
- Two SOPS files hold the secrets: `secrets/secrets.sops.yaml` (OpenTofu/mise environment) and `secrets/ansible.sops.yaml` (what the playbooks load), both encrypted with Age (`.sops.yaml` lists the recipient age public keys: `perso`, `pro` and `secours` for both files, `github-actions` — the CI's `SOPS_AGE_KEY` — for `secrets/ansible.sops.yaml` only). Post-quantum recipients only (`age1pq1…`, `age-keygen -pq`; age ≥ 1.3, sops ≥ 3.12): a single X25519 recipient would expose the data key, so `check_age_recipients.py` refuses one.
- `.sopsrc` (`ageKeyFile: /home/sylvain/.age.key`) is read only by the editor extension, not by sops: sops adds up `SOPS_AGE_KEY_FILE`, `SOPS_AGE_KEY`, `~/.config/sops/age/keys.txt` and `~/.ssh/id_ed25519` (see `docs/runbooks/test-cle-secours.md`).
- `mise.toml` auto-loads (and redacts) `secrets/secrets.sops.yaml` into task environments via `_.file`, through the sops binary (`sops.rops = false`: mise's built-in rops cannot read post-quantum `age1pq1…` recipients).
- In Ansible playbooks, secrets are loaded with:
  ```yaml
  community.sops.load_vars:
    file: "{{ playbook_dir }}/../secrets/ansible.sops.yaml"
    expressions: evaluate-on-load
    return_method: vars-only
  ```
  `return_method: vars-only` needs ansible-core ≥ 2.21 (pinned in `uv.lock`, which the lint, test and deploy workflows install with `uv sync --locked`) and fails outright below it, instead of handing the secrets back as facts: those only reached the play through the deprecated fact injection, now off (`inject_facts_as_vars = False` in `ansible/ansible.cfg`, `ANSIBLE_INJECT_FACTS_AS_VARS=False` for Molecule; read facts as `ansible_facts[...]`). **Precedence**: the secrets land in the `include_vars` layer, so they **beat** role defaults, `group_vars`/`host_vars`, play `vars:`, the `vars:` of a `roles:` entry, a role's `vars/main.yml` and block/task `vars:`, and lose only to `set_fact`/registered vars, role and include params (the `vars:` of an `include_role`) and extra vars (the play and role-entry `vars:` cases checked on 2.21.5). A key of `secrets/ansible.sops.yaml` must therefore never bear the name of a variable that a playbook or a role sets (hence `host_user_password_hash`, not a generic `password`): prefix it per instance (`prod_planning_*`, `demo_planning_*`) and hand it over in the role entry's `vars:`. `.github/scripts/check_sops_shadowing.py` (Lint workflow; `python -I .github/scripts/check_sops_shadowing.py` from the repo root) fails on any such name.
- Every key of both SOPS files has an entry in `secrets/secrets-rotation.yaml` (kind, last rotation date, procedure), checked by `.github/scripts/check_secret_rotation.py` in the Lint workflow: adding or removing a SOPS key means adding or removing its entry; after a rotation, set `last_rotated` to the day and `estimated: false` in the same commit (`docs/runbooks/rotation-des-secrets.md`).
